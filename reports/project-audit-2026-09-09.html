01 · What the audit found

The main risk is content behavior, not an obsolete stack.

High priority · reproduced

Two card contracts are broken

B144 / rw_b144: the base applies 2 Weak; upgrading it produces 0 Weak despite promising to retain that effect. Its explicit empty upgrade effect array replaces the base array.

B041 / rw_b041: promises choosing an Attack and drawing 1 card (2 upgraded). Execution automatically chooses the first Attack and draws 0 in both forms.

Direct execution against current modules confirmed these results. Fix with behavior tests for both faces, then inspect the remaining catalog.
High priority · verified code / docs mismatch

The published plan understates live scope

The roadmap and README describe 12 live designs with Smith and the generated catalog gated. Current code enables upgrades and includes all 75 designs in later-act pools, subject to learner score unlocks.

Score unlocks are not human review gates. Add explicit per-card release status shared by rewards, shops, upgrades, and validation. Preserve already-owned cards through a deliberate compatibility policy.

Smith is already implemented. Its readiness needs reconciliation, not another implementation project.
High priority · registry audit

The next CI audit can block a release

npm audit reports nanoid (high), PostCSS (moderate), and Vitest / its mocker (two moderate package findings from one advisory). CI already fails on high severity.

These are development dependency findings; this audit did not establish a shipped browser exploit. Refresh compatible packages and transitive dependencies, then rerun the audit and full checks.

Registry candidates: Vite 8.1.5 → 8.2.2; Playwright 1.61.1 → 1.63.0; Vitest 4.1.10 → 4.1.11. Evaluate Vitest 5 separately. TypeScript 7.0.2 was not reported outdated.
Medium priority · architectural risk

Session recovery is incomplete

Saves cover stable rooms, not combat or a pending cast. Storage write errors are silently swallowed. Pause-aware teaching timers are wired to the menu, but no page visibility / lifecycle handlers were found.

Add visible save status and pause-on-background behavior. First make checkpoint recovery explicit; design exact combat resume separately so reload cannot bypass a failed cast or committed death.

Browser suspension and storage denial need targeted tests and physical-device verification; this is a code-based risk assessment.

Additional correctness review: special card damage uses dealDirect(), which subtracts HP without the main hit pipeline’s Block, vulnerability, and impact events. Audit each such effect against its intended contract before unifying resolution; do not assume every special effect should behave identically.

04 · Follow the original design funnel

A completion plan with evidence at each gate.

Sequence follows ROADMAP and the Resonance Warrior playbook, corrected for code already implemented. Rough engineering effort assumes one developer; family playtesting and content review add calendar time.

Establish the release truth

2–4 developer days. Reconcile docs, catalog eligibility, Smith, and score unlocks. Patch dependency findings. Fix B144/B041 and audit related generated effects.

Exit: an explicit reviewed-content allowlist, passing regressions, clean dependency audit, and a documented migration policy.

Harden real-device play

4–7 days. Add lifecycle handling, speech failure fallback, save feedback, dialog consistency, Firefox and production gameplay coverage. Refactor only the CSS needed for verified issues.

Exit: cast-on tutorial → reward on all target engines; interruption, zoom, rotation, scrolling, and menu tests pass on representative physical devices.

Validate Act I with families

3–5 instrumentation days + playtesting. Start from the 5/4/1 deck and nine initial rewards. Keep 易傷, 練功, 轉拍, and 勁 understandable with adult coaching.

Exit: apply the documented cast-on / debug-skip matrix, recording offers, choices, HP loss, spell errors, and run duration. Agree a family session-length target.

Promote reviewed card waves

1–2 weeks per small wave. Validate already-written cards and upgrades in batches, including explicit card choices and Power timing. Keep every released card castable under parent settings.

Exit: semantic, save/load, and human review gates pass. The 75-card catalog is a design target, not a reason to publish untested cards.

Complete the three-act arc

2–4 weeks + balance cycles. Tune the existing Garden, Library, and Observatory progression. Add a small event/relic/potion slice if it improves route decisions; extend save schema and timing hooks first.

Exit: each act has a readable encounter progression, viable deck directions, meaningful rest/shop choices, and tested boss victory and defeat.

Ship v1, then expand

About 1 week after gates pass. Run production playthroughs, migration checks, curriculum checks, accessibility review, and final content/art review. Reconcile version docs and release through existing Pages CI.

Exit: one polished character and a reliable three-act run. Reassess difficulty levels, keys, Act IV, and new subjects using actual player evidence.

The playbook requires at least 30 cast-on and 30 debug-skip Act I drafts per direction plus 30 hybrid drafts before wave promotion, and contextual review of extreme pick rates after 100 human offers. Its synthetic win rates are proxy results, not proof of preschool difficulty or complete-game balance. Full-catalog completion cannot be dated credibly until this throughput is known.
